NHL shot modelling

A shot model on 956,147 attempts

Given where a shot was taken from and how, what is the chance it goes in. I built five models to answer that and scored them on 200,820 held-out shots from the 2018-19 and 2019-20 seasons. They all landed within half a percentage point of each other. Working out why took longer than building them.

The spread across the four single models is 0.005 of ROC-AUC. A gradient-boosted tree reading a flat feature table and a Transformer reading event sequences disagree by less than I would expect between two reruns with different seeds.

The ensemble buys about four thousandths of AUC over the best single model and pays for it in calibration: its expected calibration error is roughly twice the Transformer's. If the question is how to rank shots, the ensemble wins narrowly. If the question is whether a stated 8% chance really happens 8% of the time, it is the worst of the five. The XGBoost baseline is deliberately trained without class weighting so that it stays a clean reference point rather than a tuned competitor.

What the model is allowed to see

Everything above sits on one set of features, built from public play-by-play tables. The tables have their own problems and the write-up says so rather than quietly cleaning them:

  • The raw tables carry duplicated play rows for both seasons. The feature builder deduplicates on play_id.
  • The strength field is only reliable on goal rows, so shot-level strength is reconstructed from penalty windows rather than read off directly.
  • The target population is unblocked attempts, meaning shots, missed shots and goals, with empty-net goals excluded.
  • The model never observes goalkeeper position, defender locations, screens, lateral passes, or any player tracking data. None of it is in the source.

That last line is the whole result. A player on the floor tracks the goalkeeper's position, the defender's angle and whether the view is screened, continuously and without effort. Not one of those is a column here. Five architectures converge on the same number because the features are what is limiting them, not the architecture. Another layer would not have helped.

Computing what the tables omit

If a variable is missing from the event data, one option is to stop. Another is to compute it from physics instead. The second is only honest if the assumptions are written down, so they are versioned in a config file that both the Python and the browser read:

m = 0.170 kg diameter = 0.0762 m thickness = 0.0254 m ρ = 1.225 kg/m³ C_d = 0.90 area = d × t
Four modules, and what each one is entitled to claim
ModuleMethodScope
Ballistics Quadratic drag, RK4 integration, cross-checked against SciPy RK45 Illustrative trajectories under the stated assumptions
Gyroscopic stability Exact moments of inertia, assumed range for Cmα Scenario analysis. 5 and 20 rev/s are illustrative, not measured
Response sensitivity Controlled perturbations over 5,000 held-out shots Sensitivity of the fitted model, not a causal physical effect
Dimensional analysis Drag parameter β and Froude number Shows drag is non-negligible here, which is why RK4 and not a parabola

The third row is the one that is easiest to misread and hardest to resist misreading. Perturbing a feature and watching the prediction move tells you about the function that was fitted. It does not tell you what would happen on the ice if that feature actually changed. Keeping those two apart is most of the work.

Reproducing it

Every figure on this page comes from one export script in the research repository, so the page and the code cannot drift apart without someone noticing. Compact artifacts are checked in, which means the unit tests and the public-contract tests run without the multi-gigabyte raw dataset. There is a separate headless-browser check that loads the instrument and asserts the five-row metrics table, the slider interaction, the language switch and the mobile layout.

The research repository is private. The instrument linked at the top of this page is the part that is meant to be public.
